# Export POSTMORTEM DDL into the scripts

Snowflake is the source of truth; the `.sql` files are its export. This procedure brings the files up to
date. It only **reads** Snowflake: every statement here is `SHOW`, `DESCRIBE` or `GET_DDL`. Never run a
script against Snowflake as part of an export.

Run SQL with the `sql_exec` MCP tool (Claude Code) or the
`sfsehol-anthropic_snowflake_hackathon_bshkns` connection (Cortex Code / Snowflake CLI). Put any helper
scripts and dumps in a scratch directory, not in the repo.

## 1. Inventory and diff

List what exists now:

```sql
SHOW SCHEMAS IN DATABASE POSTMORTEM;
SHOW TABLES IN DATABASE POSTMORTEM;
SHOW VIEWS IN DATABASE POSTMORTEM;
SHOW USER FUNCTIONS IN DATABASE POSTMORTEM;
SHOW PROCEDURES IN DATABASE POSTMORTEM;   -- filter to is_builtin = 'N'
SHOW FILE FORMATS IN DATABASE POSTMORTEM;
SHOW SEQUENCES IN DATABASE POSTMORTEM;
SHOW CORTEX SEARCH SERVICES IN DATABASE POSTMORTEM;
SHOW SEMANTIC VIEWS IN DATABASE POSTMORTEM;
SHOW AGENTS IN DATABASE POSTMORTEM;
SHOW STREAMLITS IN DATABASE POSTMORTEM;
SHOW STAGES IN DATABASE POSTMORTEM;
SHOW WAREHOUSES LIKE 'PM_WH';
```

List what the repo has: the object files `<SCHEMA>/<type>/<NAME>.sql` (one statement each), plus the
hand-written `setup/*.sql`. Report to the user before writing anything: objects **added** in Snowflake, objects
**removed** from Snowflake, and objects in both. Removed objects get deleted from the scripts; confirm that
with the user, since a removal can be a mistake on the Snowflake side.

Skip these: `AI_OBS_OUTPUT_PARSER_*` functions and the `_PEP_YAML_READER` file format (auto-generated by
agent observability), the one-off backup tables `RESULTS.AGENT_SPEC_BACKUP` and
`RESULTS.EVAL_POSTMORTEM_ANALYST_BAK_20261023`, and the empty `RAW` and `PUBLIC` schemas. Ask before skipping any
other new backup table.

Fastest diff: `GET_DDL` needs constant arguments, so build one `UNION ALL` query with a row per object that
returns `sha2(trim(rtrim(trim(regexp_replace(GET_DDL(...), '[[:space:]]+', ' ')), ';')))`, and hash each
file's statement the same way locally (drop the `--` header, i.e. split on `;` outside quotes, `$$` blocks and
`--` comments). Objects
whose hashes match need no work; only changed and added objects need their DDL pulled in full.

Snowflake may be changing while you export (another session rebuilding an object). Check `created_on` /
`last_altered` again at the end and re-hash everything in one final pass before reporting.

## 2. Pull DDL

`GET_DDL` with fully qualified names (third argument `TRUE`):

| Object | Call |
|---|---|
| Whole schema (tables, views, functions, procedures, file formats, sequences) | `GET_DDL('schema', 'POSTMORTEM.<SCHEMA>', TRUE)` |
| Table / view | `GET_DDL('table' \| 'view', 'POSTMORTEM.<S>.<NAME>', TRUE)` |
| Function / procedure | `GET_DDL('function' \| 'procedure', 'POSTMORTEM.<S>.<NAME>(<ARG TYPES>)', TRUE)`, e.g. `'POSTMORTEM.RESULTS.SP_REPLAY(VARCHAR, VARCHAR, VARCHAR, VARCHAR)'`; argument types come from the `arguments` column of `SHOW` |
| Cortex Search service | `GET_DDL('cortex_search_service', 'POSTMORTEM.<S>.<NAME>', TRUE)` |
| Semantic view | `GET_DDL('semantic_view', 'POSTMORTEM.<S>.<NAME>', TRUE)` |
| Agent | `DESCRIBE AGENT POSTMORTEM.<S>.<NAME>`: use `comment`, `profile` and `agent_spec` (JSON) |
| Streamlit app | `GET_DDL('streamlit', 'POSTMORTEM.<S>.<NAME>', TRUE)`. Its main file (`DESCRIBE STREAMLIT`) goes in `streamlit/`, copied exactly from the stage (see AGENTS.md): read it with `SELECT md5($1), $1 FROM @POSTMORTEM.APP.APP_STAGE/<main_file> (FILE_FORMAT => 'POSTMORTEM.APP.RAW_TXT')`, write it with a script, and compare its MD5 with `LIST`. When `main_file` changes, replace the old file |
| Warehouse, stage | Not supported by `GET_DDL`. Rebuild from `SHOW WAREHOUSES` / `SHOW STAGES` (size, auto-suspend, auto-resume, stage encryption type) |

## 3. Write one file per object

Each object gets its own file: `<SCHEMA>/<type>/<NAME>.sql`, where `<type>` is one of `tables`,
`sequences`, `file_formats`, `functions`, `views`, `procedures`, `search_services`, `semantic_views`, `agents`,
`streamlits`,
and `<NAME>` is the object name as `SHOW` returns it. Warehouse, database, schemas and stages live in the
hand-written `setup/` files (`warehouse.sql`, `database_and_schemas.sql`, `stages.sql`), rebuilt from `SHOW`.

Each object file is a `--` header, a blank line, then the statement:

```sql
-- POSTMORTEM.<SCHEMA>.<NAME> (<type>)
-- <What the object is for, in a sentence or two. Write it for a newcomer: what it holds or does, not how.>
--
-- Uses: <objects it references; same-schema names unqualified, others SCHEMA.NAME>
-- Writes: <tables it inserts into, updates or deletes from (procedures)>
-- Written by: <procedures that write it (tables)>
--
-- <Known gaps, warnings. Tables: "WARNING: CREATE OR REPLACE TABLE drops existing data. Run only on a
--  fresh, empty database." Procedures that call AI_COMPLETE: "A CALL runs AI_COMPLETE (costs credits) and
--  writes rows.">
<statement>
```

- Omit `Uses` / `Writes` / `Written by` lines that would be empty. Derive them from the statement text
  (every `POSTMORTEM.<S>.<N>` it mentions; `INSERT INTO` / `UPDATE` / `DELETE FROM` targets), not from memory.
- **Changed object:** replace only the statement; keep the header's description and notes, and refresh the
  `Uses` / `Writes` / `Written by` lines (other files' `Written by` lines too, if a procedure's writes changed).
- **New object:** write a description from what the DDL does (read the body; don't guess). Masking rules apply.
- **Removed object:** delete its file, its `deploy.sql` line and its row in the folder's `README.md`, and drop
  it from other files' header lines. If a type folder ends up empty, delete the folder and its link in the
  root README's schema map.

Rules:

- Keep `GET_DDL` text verbatim. Don't reformat, re-case or re-indent: step 4 compares by hash.
- **Semantic views:** with the `TRUE` flag `GET_DDL` returns the name schema-qualified. If an account ever
  returns it unqualified, qualify it (`POSTMORTEM.<S>.PM_SV`); that is the only edit allowed.
- **Agents:** write the `agent_spec` JSON as YAML in this form, matching the existing entries. Generate the YAML
  with a script from the exact `agent_spec` string rather than retyping it; keep value types as they are in the
  JSON (some specs store `max_results` as the string `"6"`, others as the number `6`).

  ```sql
  CREATE OR REPLACE AGENT POSTMORTEM.<S>.<NAME>
    COMMENT = '<comment, single quotes doubled>'
    PROFILE = '<profile JSON>'
    FROM SPECIFICATION
  $$
  <agent_spec as YAML: block scalars (|) for multi-line instructions>
  $$;
  ```

- Keep the existing known-gap notes in headers; don't fix the gaps themselves.

Then update the indexes:

- **`deploy.sql`**: one `EXECUTE IMMEDIATE FROM './<path>';` line per file, setup first. Order: tables,
  sequences and file formats; then functions and views; procedures; search services; semantic views; agents; streamlits.
  Within that, every object must come after everything in its `Uses` line (views in particular: `GET_DDL`
  alphabetical order fails on a fresh account). Procedures may reference objects that don't exist (known
  gaps); those don't affect the order.
- **`<SCHEMA>/<type>/README.md`**: one row per object in the folder's table: link, the header description,
  and the header's `Written by` (tables), `Writes` (procedures) or `Uses` (other types). Object-specific notes
  from the header (known gaps, quirks) go in its Notes list. Keep the folder intro and type-wide notes. For a
  new type folder, write the README in the same form as the others and link it from the root README's schema
  map, with the object count.
- **Root `README.md` schema map:** update the object counts per folder if objects were added or removed.

## 4. Verify

- **Statements:** for every object file except agents, normalise whitespace (collapse every run of whitespace to
  one space, trim, drop the trailing `;`) in both the file's statement and the `GET_DDL` output, then compare
  SHA-256 hashes. Every statement must match; report the count (`n of n identical`).
- **Agents:** parse each YAML block and compare it as JSON (key order ignored) with `agent_spec` from
  `DESCRIBE AGENT`. Comment and profile must match too. To check the JSON you parse against is exact, hash it
  against Snowflake's: `EXECUTE IMMEDIATE $$ BEGIN DESCRIBE AGENT ...; LET rs RESULTSET := (SELECT
  sha2("agent_spec") FROM TABLE(RESULT_SCAN(LAST_QUERY_ID()))); RETURN TABLE(rs); END; $$`.
- **Streamlit source:** the MD5 of `streamlit/<main_file>` equals the stage file's MD5.
- **Coverage:** every object from step 1 (minus the skipped ones) has exactly one file, each file holds exactly
  one statement, and every file is listed exactly once in `deploy.sql` and in its folder's `README.md`.
- **Order:** walking `deploy.sql` top to bottom, no file uses an object that comes later.

If anything fails, fix the file and re-check. Don't loosen the comparison.

## 5. Update docs, then stop

- Update the root `README.md` (the export date, the Verification section's counts) and `AGENTS.md` if the layout or a safety-relevant object changed.
- Show the user a summary: objects added, removed and changed, and the verification counts.
- Commit only when the user asks. Never push without being asked.
